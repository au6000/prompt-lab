# ADR-0005: 判定モデルは表で引き、呼び先は /v1/decisions、モデルは事前登録で固定する

状態: 採用 (2026-11-20、0.2.0)

## 背景
0.1 はバックエンドの名前を文字列で何か所も分岐し、非推奨の `/v1/evaluate` を呼んでいました。
事前登録の lock は判定モデルを覆っていませんでした。

## 決定
判定モデルの種類 (`machine`、`fake`、`gateway`) を 1 つの表で引きます。task.json の `deciders` に名前とモデルを並べ、どのコマンドも `--decider` で選びます。

gateway は `/v1/decisions` に `{model, input, questions}` を送ります。
429 では `retry-after` を守り、5xx は間をあけて送り直し、402 では送り直さずに止めます。
鍵は `AI_GATEWAY_API_KEY` か `PLAB_KEY_FILE` からだけ読み、どの出力にも記録にも出しません。

事前登録の lock には各判定モデルの種類とモデルを含めます。

## 理由
判定モデルを選ぶのも当てはめの一種です。事前登録のあとにモデルを差し替えられると、評価の組への過学習を止められません。
判定モデルを 1 か所の表にすれば、ほかのモジュールは種類の名前を知らずに済みます。

## 捨てた案
- 名前の文字列で分岐し続ける。
- 判定モデルをプロンプトの中に書く。比べるたびにプロンプトの写しが増えます。

## 引き受けること
版の無いモデルの名前 (`typesafe-ai/jev` など) は、Gateway の側で中身が変わりえます。再現が要る研究では、版つきの名前 (`typesafe-ai/jev-1.14.0` など) を書きます。

## 確かめ方
`tests/test_gateway.py` (記録した形の返事、429、402、断り、名前や数の食い違い、鍵が出ないこと)。2026-11-20 に本物の Jev を 1 回呼んで確かめました。
